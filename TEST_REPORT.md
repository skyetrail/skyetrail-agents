Per the kickoff, this makes calibration the first thing to fix. I did not edit anything mid-test (the kickoff also says not to); this section records where the excess actually comes from, because it is mostly not the calibration section of `auditing-skills`:

1. **Cascade counting.** One missing section scores as 2 to 4 separate rule failures. Each auditor said so itself ("this single addition clears three Blocking fails"). Merged by root cause, every file has roughly 4 to 6 distinct issues, which sits at the threshold rather than triple it.
2. **Repeatability divergence on identical rules.** Three cross-run inconsistencies: the missing-baseline record scored fail / fail / warn across the three audits; the same >100-line-no-contents-list defect in `steering-rules.md` scored fail / fail / warn; dependent positional rules scored N/A by one auditor ("no section exists to position") and Fail by another. The self-audit itself warned repeat audits could diverge; the runs proved it.
3. **`steering-rules.md` "always" overreach.** The Return rules ("sections of the report are named", severity blocking, condition always) demand a named report format from in-conversation skills whose output is an artifact. This alone generates blocking fails on all three files. The condition, not the auditor, is what escalates here.

**Recommended calibration fix (for after testing):** add a one-finding-per-root-cause counting rule and explicit N/A guidance for dependent rules to `auditing-skills`; rescope the Return cluster (and reconsider "always" on the report-position rules) in `steering-rules.md`. Both are one-line-scale changes.

## Step 2: format experiment

PENDING — with one result already in that changes how to read this experiment.

**The first "no skill loaded" baseline was contaminated.** The subagent environment inherits the session's installed skills, and the bare-dispatch agent found and loaded `superpowers:writing-skills` (a third-party skill-authoring skill installed here) on its own initiative, stating so in its opening sentence. Its output was strong: valid frontmatter, gerund-form name, a what-plus-when third-person description, a copyable checklist, a bundled preflight script, one-hop structure. None of that measures unaided model knowledge.

Two consequences:

1. The baseline was re-run with skill use explicitly forbidden. That instruction is itself a small intervention, so the rerun measures "model knowledge when told to use only model knowledge", which is the closest available control in this environment. Both runs are reported.
2. This is an environmental fact that bears on `writing-skills` step 1 itself: in a session with skill-authoring skills installed, "dispatch a subagent with no skill loaded" does not produce a clean baseline unless the dispatch forbids skill use. The skill does not say that. Worth a line in the skill if the baseline gate is kept.

**Clean baseline (skills forbidden, 0 tool uses, sonnet).** The unaided model produced a valid and usable SKILL.md: correct frontmatter with only `name` and `description`, a lowercase-hyphen name (`docs-site-deploy`), a third-person description with capability and triggers, a numbered procedure with gates, a failure section, six bundled scripts one hop from the SKILL.md, and explicitly flagged judgment calls. It also caught a genuine flaw in the runbook it was given (the version bump lands after the build, so the shipped site may not carry it). Syntax and structure are not where the unaided model fails.

Where it did deviate from the house rules: its description summarises the workflow step by step (an Important fail under `skill-rules.md` Discovery), and it added a "When to use this skill" body section that duplicates the description. Those are house-specific disciplines, not format knowledge.

**With-skill arm (writing-skills loaded, sonnet, 42 tool uses).** The agent ran the skill's full workflow, and the workflow ran as designed in this environment:

- Built a disposable fixture repo in the scratchpad (real `npm run build`/`linkcheck`, inert deploy stub; no irreversible action attempted) because the brief's docs site does not exist. Reasonable initiative, honestly disclosed.
- **Nested subagent dispatch worked**, so step 1's baseline ran literally: a vague-ask baseline agent ("Can you ship the docs site update?") missed a build warning despite `WARNING:` in the output, scope-crept into `package.json` and `CHANGELOG.md`, invented a version bump, skipped the staging spot check, and dropped the Slack step, all documented in the agent's own words.
- Every rule in the produced skill traces to one of those observed failures, which is exactly the skill's step 4 discipline.
- Step 6 re-run with the drafted skill inlined: the agent held the build gate, quoted the rule, touched nothing else, and asked how to proceed. (Inlining tests the body, not description-driven discovery; the agent said so itself.)
- The step 7 audit caught a real defect: the first draft's YAML frontmatter did not parse (bare colon in the description, unquoted `#docs` read as a YAML comment). Verified with a parser, then fixed. The unaided runs never verified their frontmatter at all.

Its description is 863 characters, within the 1024 cap; noted that `skill-rules.md` nowhere states that cap, so an overrun would pass the house rules while failing the spec. Its description also front-loads the component list ("a gated build and link check, a docs/VERSION bump, ..."), which is borderline against the house "does not summarise the workflow" rule.

**Side-by-side verdict, and the direct answer the kickoff asked for:** the unaided subagent **did** write a usable SKILL.md. Format and structure are not where the unaided model fails on this task and model. What the skill changed was method, not syntax: an evidence loop that surfaced five concrete failure modes and encoded each as a rule, a scope section that the baseline agent demonstrably needed, and a verification step that caught a parse bug. The format-teaching parts of `writing-skills` steps 2 and 3 duplicated what the model already did unaided; the baseline-gate methodology and the house description/scope discipline are where the behaviour delta lives. That is the "cut steps 2 and 3 to the house-specific parts" outcome `DECISIONS.md` anticipated, now with evidence on one model (sonnet), one task, one run per arm.

One addition the experiment argues for if the baseline gate is kept: the skill should say to **forbid skill use in baseline dispatches**, since this environment's first "bare" baseline self-served from an installed skill-authoring skill.

## Step 3: description A/B

Method: six fresh sonnet subagents acted as a skill-selection layer. Each received the three descriptions (variant A verbatim, or variant B with the sibling-redirect clauses removed and nothing else changed) plus the 19-query set from `TESTING.md`, and classified each query as one of the three skills or NONE. Three runs per variant, query order rotated per run and paired across variants, with an explicit instruction to judge each query independently. Caveat, stated plainly: this measures description-driven selection in a classifier framing, not the real harness trigger path, and queries were batched per run rather than isolated per dispatch. Direction of results was decisive enough that the approximation is unlikely to flip the conclusion.

### Trigger rate on own positives (3 runs each)

| Skill | Variant A | Variant B |
| --- | --- | --- |
| writing-skills (5 queries) | 15/15 | 15/15 |
| auditing-skills (4 queries) | 12/12 | 12/12 |
| writing-agents (4 queries) | 11/12 | 12/12 |
| **Total** | **38/39 (97%)** | **39/39 (100%)** |

Variant A's single miss: "Fan this out across the eight transforms" → NONE once, reasoned as an execution request rather than prompt-writing. Variant B never missed it.

### False fires on the negatives

Zero, both variants: 9/9 NONE for A, 9/9 NONE for B. No overtriggering observed anywhere.

### The three ambiguous queries

| Query | Variant A (3 runs) | Variant B (3 runs) |
| --- | --- | --- |
| Why is my skill not triggering? | auditing-skills ×3 | auditing-skills ×3 |
| Improve this skill. | writing-skills ×3 | writing-skills ×3 |
| Review my agent setup. | auditing-skills ×3 | auditing-skills ×2, NONE ×1 |

Both skills' descriptions claim the not-triggering case; selectors consistently resolved the "why" framing to the auditor, which is a useful outcome under either variant since the auditor redirects onward. "Improve this skill" resolved to writing-skills every time in both variants. The single divergence in eighteen ambiguous classifications is one B run sending "Review my agent setup" to NONE ("matches no listed trigger precisely").

### Recommendation on the redirect clauses

**Cut them.** `TESTING.md`'s own criterion was that if variant B handles the ambiguous queries as well as variant A, the clauses cost description space for nothing. B matched A on 17 of 18 ambiguous classifications and beat A on positives (the one A miss was a writing-agents positive, the skill whose description is longest). The redirect information already exists in each body's "Where this stops" section, so nothing is lost at the point where it is actually used. The one X3→NONE result is the only trace of a benefit and is noise-level against A's own G3→NONE miss.

## Decisions I would revisit

Open items in `DECISIONS.md`, now with evidence:

- **Redirect clauses: cut them.** The A/B answered the open question directly; see step 3. The clauses buy no trigger benefit and the same information sits in each body.
- **Format guidance: cut steps 2 and 3 of `writing-skills` to the house-specific parts.** The clean baseline shows sonnet writes valid frontmatter and structure unaided; what it does not do unaided is the house description discipline (it summarised the workflow in the description), the scope boundary, or any verification. Keep the artifact-choice gate, the baseline methodology, the description rules, and the audit step; drop the parts that teach format the model already has. This is the outcome `DECISIONS.md` anticipated, now with one-model evidence rather than none.
- **Boundary rules marked blocking: keep blocking.** The unprimed probe is direct evidence for the severity: with no stated scope behaviour, the auditor forced an audit onto a file outside its own two target kinds. The one observed failure `DECISIONS.md` cites now has a second, local reproduction.

Settled decisions I would not reopen, with one adjacent note: the flat rule format stands, but the **conditions on the Return cluster in `steering-rules.md`** ("always") are what generated cross-file blocking noise in step 1. Rescoping those rows to hand-off (or reused-with-report) is a condition tweak inside the settled format, not a format change.

Two additions the testing argues for that no decision covers:

- `writing-skills` step 1 should say to **forbid skill use in baseline dispatches**; this environment's first bare baseline self-served from an installed skill-authoring skill.
- `skill-rules.md` carries none of the spec's mechanical limits (name charset, 1024-character description cap). With no lint script in this repo anymore, nothing else checks them; either add the two rows or state the reliance on external tooling.
